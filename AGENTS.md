# AGENTS.md

## Project state

A QQ chat bot on Drogon. The in-project plugin `controllers::AssistantBot` connects two sibling plugin libraries: `drogon-onebot` receives OneBot v11 events from NapCat and sends messages through its HTTP API, and `drogon-openai` asks an OpenAI-compatible model (DeepSeek in `config.json`) for the replies. The bot defaults to answering private text messages from every friend of its QQ account and supports explicitly enabled groups. Optional roles, memory, tools, MCP, and scheduled tasks are described below. The admin access page can restrict replies to an allowlist and block senders with a blacklist; SQLite persists the policy. NapCat is not deployed yet: the tests use fakes, and `scripts/chat.py` stands in for NapCat by hand.

- `src/main.cpp` starts `drogon::app()` from `config.json`, resolved against the working directory (`just run` uses the repo root). Listeners, threads, and logging live there; the default is `127.0.0.1:8080`.
- `main.cpp` registers two beginning advices. `check_bot_plugin` logs FATAL and aborts when `controllers::AssistantBot`, `admin::Auth`, or `admin::Runtime` is not loaded, because drogon only logs an unknown plugin name and keeps running. `print_routes` prints the listener addresses and every route (`getHandlersInfo()`); the route table is only filled inside `app().run()`, so querying it before `run()` returns nothing.
- `config.json` is tracked and must stay free of anything private, because the repository is public. Without it, startup aborts with `Config file config.json not found!`. `just publish` does not install it.
- `config.json` registers six plugins and names four environment variables: `ONEBOT_ACCESS_TOKEN`, `ONEBOT_SECRET`, `DEEPSEEK_API_KEY`, and `ASSISTANTBOT_ADMIN_TOKEN`. Secrets are never read from config.json. There used to be a gitignored `config.json` copied from a tracked `config.json.example`; a stale copy then aborted startup, so the example was folded into the tracked file. A plugin whose named variable is unset or empty throws from `initAndStart`, which ends `app().run()` with its message.
- `config.json` sets `document_root` to `frontend/dist`, so the bot serves the built admin pages (see Frontend). Drogon creates `upload_path` (`tmp/00`..`FF`) on startup, under `document_root` unless the path is absolute. `config.json` gives the absolute `/tmp/assistantbot/uploads`, and `tests/config.json` keeps both under `/tmp`, so nothing is created in the repo or in `dist/`.
- `frontend/` holds the admin web pages, a Vue app whose build drogon serves from `document_root`; see Frontend.
- The plugin `storage::Database` keeps the bot's data in a SQLite database, `data/assistantbot.db` by default; see Storage. `data/` is gitignored.
- `src/controllers/` (namespace `controllers`) holds the entry points, one subdirectory per source of requests: the HTTP controllers of the admin pages in `admin/`, and the bot plugin `controllers::AssistantBot`, which handles OneBot events, in `onebot/` (see Bot). The subdirectories add no namespace level. The HTTP controllers are `drogon::HttpController<T>` subclasses. They register their routes automatically through a static registrator before `main` runs, so `main.cpp` does not include them. Adding the `.cpp` is enough.
- Use `ADD_METHOD_TO` with absolute paths. Every route starts with `/api` (e.g. `/api/admin/health`), and the routes for the admin pages with `/api/admin/`. They answer errors with a JSON body `{"error": "<message>"}`, which the pages' `request()` reads. `METHOD_ADD` prefixes the namespace-qualified class name, which would give `/controllers/Admin/...`.
- Handlers are coroutines: `auto Health(drogon::HttpRequestPtr req) const -> drogon::Task<drogon::HttpResponsePtr>`, ending in `co_return`. Take `req` by value; drogon's coroutine traits don't match `const HttpRequestPtr&`, and a reference would dangle across `co_await`.

### Bot

The bot has three parts. The plugin `controllers::AssistantBot` in `src/controllers/` receives the message events and decides how to answer each one. The workflow in `src/workflow/` (namespace `workflow`) controls access with `AccessControl` and answers chat messages with the model through `BotConfig`, `BotSettings`, `PrivateChat`, and `SessionStore`. Both use the text helpers in `src/common/` (namespace `common`), which are pure functions. Each item below names its files, and unqualified names are in that file's namespace. `docs/*/bot.md` is the user guide; update both copies with every behavior change.

- `controllers::AssistantBot` (`src/controllers/onebot/assistant_bot.*`) is a `drogon::Plugin`. Its config.json entry comes after `drogon_onebot::OneBotClient`, `drogon_openai::OpenAIClient`, and `storage::Database` and lists the three under `dependencies`, so drogon initializes them first. `initAndStart` fetches the three plugins (throwing `std::invalid_argument` if one is missing), creates a `workflow::BotSettings` from its config and the database, creates shared `workflow::PrivateChat` and `workflow::AccessControl` state, and registers a message handler with `OneBotClient::OnMessage` that captures them and calls `handle_message`.
  - Registering from `initAndStart` is what drogon-onebot documents: handlers must exist before the listeners start, and a dependent plugin's `initAndStart` runs before them.
  - `getPlugin<T>()` caches its first result in a function-local static, so call it only after `run()` has started.
  - Both libraries are static. The `getPlugin` calls reference their plugin classes, so the linker keeps them.
  - Creating `BotSettings` reads the database synchronously. That is safe there, because drogon runs every `initAndStart` on the thread that calls `app().run()` before any event loop starts, and the SQLite client runs on a thread of its own.
  - The OneBot plugin needs `event_path`; without it, `OnMessage` only logs a warning and no event arrives.
- `handle_message` (anonymous namespace in `src/controllers/onebot/assistant_bot.cpp`) runs once per message event:
  - It logs the event at INFO with `common::describe_received`, group messages included.
  - It accepts private friends and explicitly enabled groups, then checks pause and one immutable access snapshot before commands or queuing. Group defaults, mentions, administrator commands, and negative conversation keys are described below. Every private friend or group message is appended through `PrivateChat::Observe`, with `paused`, `blacklist`, or `outside_allowlist` recorded for ignored messages. Excluded messages trigger no command, context mutation, text-only notice, or model call. It packs the bot's QQ number, the friend's, and their nickname into a `workflow::Peer`, which the workflow takes for the log.
  - An atomic pause flag, shared with the handler, drops new messages before commands or queuing. Already accepted work continues. `Paused` and `SetPaused` expose it; startup resets it to false.
  - Accepted HTTP images may first use the vision role; an empty prompt without a usable image description answers `TEXT_ONLY_REPLY`, and `/help` and `/reset` are answered directly (`/reset` calls `PrivateChat::Reset` first), all through `PrivateChat::Send`. Any other text goes to `PrivateChat::Chat`.
  - The commands and the texts it answers with (`HELP_COMMAND`, `RESET_COMMAND`, `HELP_REPLY`, `RESET_REPLY`, `TEXT_ONLY_REPLY`) are constants in `assistant_bot.hpp`; the tests and `docs/*/bot.md` quote them.
- `parse_bot_config` (`src/workflow/bot_config.*`) reads the plugin config into `BotConfig`. Every key is optional: `system_prompt` (default `DEFAULT_SYSTEM_PROMPT`; empty sends none), `history_turns` (10), `idle_reset_minutes` (30), `request_timeout` (90 s), `max_tokens` (unset), `max_reply_chars` (1500), and `model` (empty, using the OpenAI plugin default). `max_tokens: null` removes a limit. Idle minutes must fit the steady clock duration, and timeout must be finite and positive. It throws `std::invalid_argument` with `controllers::AssistantBot: <key> ...`. `BOT_CONFIG_KEYS` lists the keys. Add a key to `BotConfig`, `BOT_CONFIG_KEYS`, `parse_bot_config` and the key table in its doc comment (both copies), `test_config`, `config.json`, and the tables in `docs/*/bot.md`.
- `BotSettings` (`src/workflow/bot_settings.*`) overlays the overrides saved in the database (the settings row `BOT_SETTINGS_NAME`, `bot`) on the plugin config, and hands out `std::shared_ptr<BotConfig const>` snapshots under one mutex.
  - The constructor reads the overrides synchronously and parses config.json's config first, so its errors keep their message. Invalid saved overrides throw the same message followed by ` (in the settings saved in the database)`.
  - `Update` takes a whole new override object, so `{}` restores config.json. It rejects keys outside `BOT_CONFIG_KEYS`, validates the merge with `parse_bot_config`, saves, and only then swaps the snapshot, so a failure changes nothing. A second `Update` while one is saving throws `std::runtime_error`, because the database and memory could otherwise end up in different orders.
  - `GET/PUT /api/admin/bot-config` exposes current values, overrides, config defaults, and the built-in prompt through `Describe` and `Update`; `max_tokens: null` clears a limit. `AssistantBot::Settings()` exposes the shared manager. The API returns validation messages unchanged, 409 for overlapping saves, and 500 for storage failures.
- `AccessControl` (`src/workflow/access_control.*`) loads the `access` settings row synchronously during bot initialization; missing data defaults to `all_friends` with empty lists, while malformed saved policies stop startup. `AssistantBot::Access()` exposes the shared manager; the event handler captures it by value along with chat and pause state.
  - `AccessPolicy` holds an `AccessMode` and two sets of signed 64-bit QQ numbers. `Allows` checks blacklist membership first, then `all_friends` or allowlist membership. Both lists survive mode switches and may contain the same QQ number.
  - `SetMode` and `SetListed` derive changes from the current snapshot under a short mutex, save the whole JSON document, then publish the new immutable snapshot. A failed save releases the write claim without publishing; overlapping writes throw `AccessConflict`. No database query occurs for an incoming message, and no lock spans `co_await`. Changes affect newly accepted messages; in-flight and queued work continues.
  - Saved lists and administrative QQ fields are decimal strings to preserve precision in JavaScript. `parse_qq` accepts digits only, normalizes leading zeroes, and requires a positive signed 64-bit value. HTTP bodies accept strings only.
- `PrivateChat` (`src/workflow/private_chat.*`) offers `Chat`, `Reset`, and `Send`:
  - `Chat` queues the text with `SessionStore::Enqueue`, and only a call that gets the claim loops over `TakePending`, calling `answer` for each merged prompt.
  - `answer` takes one `BotSettings::Current()` snapshot and uses it to the end, so a settings update applies from the next reply. It sends the system prompt, the recorded turns, and the prompt, with `request_timeout`, `max_tokens`, and an optional per-request model override. A failed request or a reply without text sends `FAILURE_REPLY` and adds no model turn. Incoming messages and attempted outgoing notices still enter chat records. Otherwise it strips Markdown, records the turn under the generation it read, splits the reply at `max_reply_chars`, and sends the parts in order.
  - `Reset` forwards to `SessionStore::Reset`. `Send` logs each sent part at INFO with `common::describe_sent`, or a failure at ERROR, and appends its delivery status to SQLite. `Observe` appends incoming friend messages, including ignored ones; accepted messages update session identity and UTC activity. Saved messages publish `message_created`; claim and reset changes publish `session_updated`. Storage errors are logged without stopping replies.
  - A `catch (...)` in `Chat` releases the claim and rethrows, since a claim left behind would queue that user's messages forever. drogon-onebot logs the exception.
  - Each completed model request appends a `storage::UsageRecord`, including failures, missing reports, and optional cache hits. Standard `prompt_tokens_details.cached_tokens` takes precedence over DeepSeek raw `prompt_cache_hit_tokens`; unknown cache values remain NULL. Successful storage broadcasts `usage_updated`. Storage errors are logged and replies continue. `SessionCount` forwards to `SessionStore::Count`, which reads the map size under its mutex, including empty or reset sessions.
  - `FAILURE_REPLY` is a constant in `private_chat.hpp`; the tests and `docs/*/bot.md` quote it.
- `SessionStore` (`session_store.*`) holds each user's turns, queue, claim, generation, and last activity under one mutex. Never hold the lock across `co_await`.
  - `Enqueue` clears the history first after `idle_reset` of silence, then queues the message and grants the claim only if nobody holds it. `TakePending` joins the queue with `\n`, and releases the claim when the queue is empty.
  - `Reset` clears the history and queue and bumps the generation, so `Record` drops a reply that was in flight. `Release` frees the claim after a failure.
  - History lives in memory only and is lost on restart.
  - `PrivateChat` binds it to shared `BotSettings`; history/idle limits come from a current immutable snapshot before taking the store mutex on each relevant operation. `Summaries` and `Detail` copy metadata and turns under the mutex; detail reads do not create unknown sessions. Administrative snapshots expose current limits, and queue/history/write operations trim excess turns.
- `common/text.*`: `describe_received` builds that log line, `(<self_id>) 接收 <- 私聊 <name>(<user_id>) <content>` or `(<self_id>) 接收 <- 群聊 (<group_id>) <name>(<user_id>) <content>`, where the name is the sender's group card or else nickname, showing `text` segments as they are, `at` as `@<qq>`, and other segments as `[<type>]`. `describe_sent` builds `(<self_id>) 发送 -> 私聊 <nickname>(<user_id>) <text>` for `PrivateChat::Send`. `extract_text` joins the `text` segments. `strip_markdown` drops code fence lines and heading markers (1 to 6 `#` and a space), and removes `**` and backticks outside fences. `split_reply` counts UTF-8 code points, cuts at line breaks where possible, and needs a positive `max_chars`, which `parse_bot_config` guarantees.
- Coroutines take their parameters by value. `PrivateChat`'s member coroutines use `this` across `co_await`. That is safe because `handle_message` takes the `std::shared_ptr` by value, the handler lambda holds another copy, and drogon-onebot keeps a copy of the handler in each event's `async_run` frame.
- The event route answers 204 before any handler runs, so a slow model never holds up NapCat, and quick operations (a `reply` in the response body) are not available.

### Storage

`src/storage/` (namespace `storage`) holds everything that talks to SQLite; the rest of the code calls its functions and writes no SQL.

- `Database` (`database.*`) is a `drogon::Plugin`. Its one key is `data_dir`, a non-empty string that defaults to `data` and resolves against the working directory. `initAndStart` calls `open_database`, `Client()` hands out the `DbClientPtr`, and `shutdown` drops it. Plugins that use it list it under `dependencies`.
- `open_database` creates the directory, opens `assistantbot.db` once with `sqlite3_open_v2` (`check_openable`), then creates drogon's client with one connection and runs `migrate`. It blocks, so call it only where no event loop runs.
  - `check_openable` exists because drogon 1.9.13 only logs a file that SQLite cannot open, retries a second later, and then aborts the process with `Resource deadlock avoided`.
  - The connection string quotes the path (`filename='...'`, with `\` and `'` escaped), because drogon splits an unquoted value at spaces.
  - With one connection, statements run one at a time, in the order they are sent, on the connection's own thread. `migrate` relies on that for its `BEGIN`/`COMMIT`, and `test_bot_settings` to hold a write back behind a slow query.
- Coroutine queries go through `storage::query` (`query.hpp`), which retains bound values and queues both successful and exceptional continuations back onto the caller's original event loop. Drogon's SQLite awaiter otherwise resumes on the database thread, moving HTTP clients and final client ownership there and risking a connection joining its own thread during shutdown. Test callers without a running loop may use `sync_wait`; startup helpers remain synchronous. Caller loops must remain running until their storage tasks complete.
- `migrate` (`schema.*`) keeps the number of applied migrations in `PRAGMA user_version`, so a new database runs them all. Each migration is a list of single statements, because drogon's SQLite client rejects several in one string. They run inside `BEGIN IMMEDIATE`…`COMMIT` together with `PRAGMA user_version = N`, and roll back on failure. A database above `latest_schema_version()` is rejected. Only append migrations, since a database that ran one keeps its version, and make tables `STRICT`.
- Schema version 1 has one table, `settings (name TEXT PRIMARY KEY, value TEXT)`, where `value` is a JSON document. `load_setting` (`settings.*`) reads one synchronously, for startup; `save_setting` upserts one as a coroutine, for handlers. They throw drogon's `DrogonDbException`s, or `std::runtime_error` for a row that is not JSON.
- Schema version 2 appends `model_usage` and its timestamp index. `record_usage` and `summarize_usage` (`usage.*`) save completed model requests and sum an exclusive-upper-bound UTC interval as coroutines. Missing token reports are SQL NULL; totals include only reported tokens.
- Schema version 3 adds append-only `chat_messages` with a `(user_id, id)` index; `messages.*` appends each incoming or outgoing part, returns bounded stable-ID pages (`before` or `after`), and discovers peers after restart. IDs and QQ numbers are JSON strings; timestamps are UTC Unix seconds. Stored messages never rebuild model context.
- Schema version 4 adds nullable `cached_tokens` to existing usage rows. `usage_report` returns total, independent UTC today, daily, and friend aggregates in one SQL statement so all buckets share a SQLite read snapshot. Missing reports remain distinct from known zero values.
- The plugin's and `migrate`'s own errors start with `storage::Database:`.

### Administration

- `sessions`, `reply_settings`, `usage_stats`, `logs`, and `streams` controllers implement session snapshots/reset/history, live reply configuration, UTC usage queries, process logs, and real WebSockets. All are covered by the existing authentication advice. QQ and cursor validation is strict; message pages are limited to 200, log reads to 5000, and usage intervals to 366 days.
- `admin/live_events.*` starts from Auth's beginning advice after all plugin configuration exists. It chains Trantor's original output and flush callbacks into a 5000-record ring, redacts actual configured secrets, and delivers bounded 200-record log batches once a second. Logging never sends WebSocket frames directly. `GET logs` and log subscriptions share minimum-level, keyword, and complete decimal QQ filters, a monotonic cursor, and truncation reporting. `PUT log-level` calls Trantor and is not persisted.
- `/api/admin/ws` defaults to all friends; `{type: "subscribe", user_id: "12345"}` selects one friend and null restores all. Message and session events follow that filter; usage and settings changes broadcast to everyone. `/api/admin/logs/ws` waits for a subscription with optional level/keyword/qq/after fields. Log batches echo canonical filters to let clients reject old subscriptions.
- Auth validates and registers a stream under its session mutex through `AttachStream`, atomically with revocation. Streams retain the original absolute expiry, close on logout/rotation/eviction, and expire from the delivery timer. Browser upgrade Origin must match Host. Registry callbacks never call back into Auth while holding their own mutex; no plugin pointer is retained by the logger.

- `admin::Auth` (`src/admin/auth.*`) reads `admin_token_env` using portable `read_env` (`_dupenv_s` on Windows), rejecting missing, empty, or longer-than-4096-byte values. It never logs or returns the token. `constant_time_equal` compares fixed-size SHA-256 digests without early exits.
- Its pre-routing advice covers `/api/admin` and `/api/admin/`, case-insensitively, including WebSocket upgrades and unknown routes. Only `health`, `auth/login`, and `auth/status` are public. Rejections use JSON 401. Pre-sending advice marks administrative responses `no-store` and `nosniff`.
- `controllers::Admin` serves health and login/status/logout. Login validates `{token}`, creates a random 32-character session ID, revokes the browser's old session, and sets a host-only `HttpOnly`, `SameSite=Strict`, `/api/admin` cookie with a twelve-hour maximum age. A mutex guards absolute steady-clock expiry and revocation. At most 256 sessions are retained; login prunes expired sessions and evicts the oldest when full. Logout revokes the session and expires its cookie. Sessions disappear on restart.
- `admin::Runtime` (`src/admin/runtime_state.*`) depends on the bot, OneBot, OpenAI, and database plugins. `Status` concurrently calls typed `GetLoginInfo`, `GetStatus`, and `GetVersionInfo` with two-second timeouts, returns partial upstream failures as null, and includes `ASSISTANTBOT_VERSION` (from `project(VERSION)`), plugin startup time, configured model, session count, pause flag, and daily usage. QQ numbers are strings in administrative JSON.
- Daily usage uses UTC midnight boundaries consistently, returned as `today_usage.from`, `to` (exclusive), and `timezone`. It includes request/success counts, reported-token request counts, and input/output/total tokens. A success means usable model reply text; delivery failures are separate.
- The runtime plugin samples RSS, peak RSS, and threads at startup and every sixty seconds. Its mutex-protected deque holds at most 1440 samples. The timer captures weak shared state and is invalidated at shutdown. Linux reads `/proc/self/status`; Windows uses process APIs (linked with Psapi); unavailable measurements serialize as null.
- `controllers::RuntimeController` serves `GET status`, `GET/POST bot-status` (`{paused: boolean}`), and `GET process-metrics`. All are authenticated. Pause and metrics are in memory only; usage is persistent.
- `controllers::AccessController` serves authenticated `GET/PUT access` (`{mode}`), `GET/POST allowlist` and `blacklist` (POST `{qq}`, response `{qqs}`), and `DELETE allowlist/{qq}` or `blacklist/{qq}`. Adds/removes are idempotent. Invalid bodies or QQ numbers return 400, write contention 409, and storage failures 500. `GET friends` calls typed `GetFriendList` with a two-second timeout and returns identities plus `in_allowlist`, `in_blacklist`, and `allowed` from one snapshot; upstream failures return 502 without affecting local lists.

### Dependencies

- Dependencies come from vcpkg in classic mode (there is no `vcpkg.json`). vcpkg supplies drogon with its `sqlite3` feature (which pulls in `orm` and the `sqlite3` port), and Lua with its `cpp` feature: `just init` runs `vcpkg install 'drogon[sqlite3]' 'lua[cpp]'`. The libraries install plain `drogon`; sharing a vcpkg root with them is fine, since features only add. Add a package only when code uses it. Install packages once into the vcpkg root; configure does not install vcpkg packages and fails at `find_package` if one is missing. The base preset sets `toolchainFile` to `$env{VCPKG_ROOT}/scripts/buildsystems/vcpkg.cmake`, so `VCPKG_ROOT` must be set. Packages are found under `$VCPKG_ROOT/installed/<triplet>/` (e.g. `x64-linux`), and versions are whatever that vcpkg checkout provides.
- Drogon (HTTP framework) is linked as `Drogon::Drogon` via `find_package(Drogon CONFIG REQUIRED)`. Without the `sqlite3` feature, drogon's `newSqlite3Client` logs FATAL and exits at runtime, so `CMakeLists.txt` stops configure when drogon's package defines no `SQLite3_lib` target. `assistantbot-core` also links `SQLite3_lib` directly, because `storage::open_database` calls the SQLite C API.
- The sibling plugin libraries come from CPM, not vcpkg: `drogon-openai` (OpenAI-compatible API client, https://github.com/yizhinailong/drogon-openai) and `drogon-onebot` (OneBot v11 client, https://github.com/yizhinailong/drogon-onebot). Each `CPMAddPackage` pins a release tag: `v0.3.0` of drogon-openai and `v0.5.0` of drogon-onebot. Link them as `drogon-openai::drogon-openai` and `drogon-onebot::drogon-onebot`, and include `<drogon_openai/...>` and `<drogon_onebot/...>`. As CPM subprojects their tests and install rules are off, they build as static libraries with this project's `-std=gnu++26`, and `just publish` installs only `assistantbot` and its admin pages.
- `cmake/CPM.cmake` is a bootstrap that downloads CPM 0.43.2 itself, into `$CPM_SOURCE_CACHE/cpm/` when that environment variable is set or into the build tree otherwise. The presets must not forward it with `$penv{}`: on a machine without it, that defines it as empty, and the bootstrap then downloads to `/cpm/` and fails.
- With `CPM_SOURCE_CACHE` set, CPM clones each library once into `$CPM_SOURCE_CACHE/<name>/<hash>/`, and every build tree reuses that checkout. Without it, each build tree clones into `build/<preset>/_deps/<name>-src/`.
  - The hash comes from the `CPMAddPackage` arguments, not the commit, so a new `GIT_TAG` gets its own directory. To move to a newer library release, tag it in the library first, then change `GIT_TAG`. Editing `CMakeLists.txt` re-runs configure on the next build, which clones the new tag and needs network access.
  - Do not point `GIT_TAG` at a branch again: with a shared cache the hash stays the same, so new commits are never fetched. Tracking `master` once needed `NO_CACHE YES`, which re-fetches on every configure. To try an unreleased library change, build against a local checkout instead.
- To build against a local checkout instead, pass `-DCPM_<name>_SOURCE=<absolute path>`, e.g. `just configure debug -DCPM_drogon-openai_SOURCE=$PWD/../drogon-openai` (or `CPM_drogon-onebot_SOURCE` with `../drogon-onebot`). The path must be absolute; a relative one fails inside FetchContent. Edits there are picked up on the next build. `just configure debug --fresh` drops the override.

## Tests

The tests use drogon's own framework, `drogon/drogon_test.h`, which is installed with drogon, so the tests add no dependency. They follow `../drogon-onebot`'s and `../drogon-openai`'s setup.

- `tests/CMakeLists.txt` globs `tests/test_*.cpp` (non-recursive, `CONFIGURE_DEPENDS`) and builds each file into its own executable named after the file stem, linking `assistantbot-core`. Adding a `tests/test_*.cpp` file is enough. Removing one leaves its old binary until `just clean`.
- Each executable is registered with CTest with `WORKING_DIRECTORY` at the repo root and `TIMEOUT` 60. `RESOURCE_LOCK test_config_listener` serializes them under `ctest -j`, because the app-backed tests share the listener port.
- `tests/config.json` (tracked, no secrets) is the shared fixture; the tests rely on its values:
  - It listens on `127.0.0.1:18082`. `../drogon-onebot` uses 18080 and `../drogon-openai` 18081, so all three suites can run at once.
  - The OneBot plugin's `base_url` is `http://127.0.0.1:18082/napcat`, with `event_path` `/onebot/event` and `secret_env` `ASSISTANTBOT_TEST_SECRET`. The OpenAI plugin's `base_url` is `http://127.0.0.1:18082/v1` with `model` `fake-model` and no key.
  - The bot keeps 2 turns, waits 5 s for the model, and splits replies at 100 characters.
  - `storage::Database` uses `data_dir` `/tmp/assistantbot-test/data` (`DATA_DIR` in `support.hpp`).
- `tests/support.hpp` holds the shared helpers:
  - `load_config` sets `ASSISTANTBOT_TEST_SECRET` and `ASSISTANTBOT_TEST_ADMIN_TOKEN`, removes `DATA_DIR`, then loads `tests/config.json`. Every app-backed test calls it, because the OneBot plugin throws without the variable, and each program starts with a new database.
  - `login_admin` exchanges the test token for a session through the real HTTP endpoint.
  - `fresh_directory` gives a test an empty directory under the system's temporary directory, for a database it opens itself with `storage::open_database`.
  - `run_tests_with_app` follows the libraries' copy, including `prints_and_exits` for `-l` and `-h`. Its optional pre-quit hook lets `test_private_chat` wait for persisted delivery attempts, idle session claims, and queued I/O continuations before destroying event loops; a fake NapCat request wakes its observer before the real workflow has finished recording the response.
  - `post_event` serializes an event, signs it with `hmac_sha1_hex` as NapCat does, and posts it from the test thread, which runs no event loop. `read_json` parses a tracked JSON file.
- The executables take drogon's test options: `-r <name>` runs one `DROGON_TEST`, `-s` prints passing checks, and `-l` lists the tests.

## Frontend

The admin pages live in `frontend/`: a Vue 3, Vite, and TypeScript app managed with pnpm. `packageManager` pins pnpm 12.15.0, and `engines` asks for Node.js `^22.18.0 || >=24.12.0`. create-vue generated the project; the router, ESLint, oxlint, and Prettier setup are what create-vue 3.24 generates with `--ts --router --eslint --prettier`. `docs/*/admin.md` is the user guide; update both copies when the pages or their routes change.

- `src/main.ts` mounts `App.vue` with the router of `src/router/index.ts`. `App.vue` is the layout: a sidebar with one `RouterLink` per entry of `pages`, and the `RouterView`. Views go in `src/views/`. A new page needs its view, a route, and an entry in `pages`.
- The router uses `createWebHashHistory`, so every page loads from `/` and drogon needs no fallback route for page paths. Unknown paths redirect to `/`.
- `src/api/client.ts` holds `request<T>()` and `ApiError`, and `src/api/admin.ts` one typed function and answer type per route. `request()` sends a body as JSON, resolves an empty answer to `undefined`, and throws `ApiError` with the HTTP status (0 when the bot was not reached) and the message of an `{"error": "..."}` body or the status line. A 401 redirects to login with an internal return route; the auth endpoints handle their own 401 responses. The router checks session status on navigation, and network failures let the page render its connection error instead of cancelling initial navigation.
- Texts on the pages are Simplified Chinese; code comments are English.
- `src/assets/main.css` defines the color variables on `:root`, with dark values under `prefers-color-scheme: dark`, and the shared element styles. Components keep theirs in `<style scoped>`. There is no UI library.
- `vite.config.ts` forwards `/api`, WebSockets included (`ws: true`), to `http://127.0.0.1:8080`, the default listener of `config.json`.
- `config.json`'s `document_root` is relative (`frontend/dist`) and resolves against the working directory, so `just run` serves the built pages. Without a build, `/` answers 404 and the bot runs normally.
- `CMakeLists.txt` installs `frontend/dist/` into `assistantbot/frontend/dist` under the install prefix, so the same relative `document_root` works from `publish/assistantbot/`. Configure and build don't need Node.js, but `cmake --install` fails while `frontend/dist/` is missing; `just publish` builds the pages first.
- `pnpm check` runs `type-check` (`vue-tsc --build`), `check:oxlint` (`--deny-warnings`), `check:eslint` (`--max-warnings 0`), and `check:format` (`prettier --check` on `src/`). `pnpm lint` and `pnpm format` apply the fixes. `.prettierrc.json` drops semicolons, uses single quotes, and wraps at 100 columns, and `.editorconfig` matches it. As create-vue sets it up, Prettier covers only `src/`.
- `LoginView` submits the token and returns to the original route. `OverviewView` refreshes status and metrics every sixty seconds, toggles pause, displays daily UTC usage and threads, and uses `MemoryChart` for RSS and peak RSS (pointer/keyboard selection and a data table). The frontend has no permanent test runner yet.
- `SessionsView` at `/#/sessions` merges persisted and live messages by decimal string ID, paginates older history, and uses a separate HTTP cursor for reconnect catch-up so a newer live frame cannot skip missing records. It shows memory context and resets it through the shared workflow.
- `ReplySettingsView` at `/#/settings` edits all seven reply fields with save and restore-default actions, including multiline prompts and per-request model selection. `UsageView` at `/#/usage` uses explicit UTC day ranges, daily bars with a data table, and friend rankings. `LogsView` at `/#/logs` supports filters, pause/resume, auto-scroll, ring-gap warnings, and runtime log level changes.
- `useAdminStream` authenticates and reconnects sockets with bounded exponential retry and restores subscriptions. Log clients preserve their last examined cursor while paused and replay retained entries on resume.
- `AccessView` at `/#/access` saves the mode explicitly and edits allowlist/blacklist entries immediately. Its searchable table combines NapCat friends and list-only QQ numbers; manual entry still works when the friend query fails. Local policy responses drive membership and reply labels. Writes and refreshes disable conflicting controls; failed policy reads disable writes until refresh succeeds.

## Commands

`just` drives the build. Recipes map onto CMake presets named `<os>-<profile>` (`linux-debug`, `linux-release`, `windows-debug`, `windows-release`), with build trees in `build/<preset>/`.

- `just init`: `vcpkg install 'drogon[sqlite3]' 'lua[cpp]'` (classic mode, no `vcpkg.json`; `VCPKG_ROOT` must be set). The libraries' `init` installs plain `drogon`.
- `just build [debug|release]`: configure only if `build/<preset>/CMakeCache.txt` is missing, then `cmake --build --preset` (default `debug`), then copy `compile_commands.json` to `build/` for clangd. A cache left by a failed configure makes this skip configure and fail with `loading 'build.ninja'`; fix it with `just configure debug --fresh`.
- `just configure [profile] [args]`: force a configure. Use `just configure debug --fresh` after changing `CMakePresets.json` (preset changes are not picked up by automatic re-configure).
- `just run [profile]`: build, then run `build/<os>-<profile>/assistantbot`.
- `just test [profile]`: build, then `ctest --preset <os>-<profile>` (output on failure; no tests is an error). Run one test program from the repo root with `build/linux-debug/tests/<name>`.
- `just publish [profile]`: build (default `release`), build the admin pages (`frontend-build`), and `cmake --install` into `publish/assistantbot/`. This needs pnpm, unlike the libraries' `publish`.
- `just clean [profile]`: delete `build/<os>-<profile>/`, or `build/` and `publish/` when no profile is given. The library clones in `_deps/` go with the build tree, so the next configure clones them again. Installed vcpkg packages live outside the repo and are not affected.
- `just docs`: create `build/doxygen` (Doxygen does not create the output path) and run `doxygen Doxyfile`; open `build/doxygen/html/index.html`.
- Without just: `cmake --workflow --preset linux-debug` configures, builds, and tests.
- `just frontend-init`, `frontend-dev`, `frontend-build`, `frontend-check`, and `frontend-fix` run `pnpm install --frozen-lockfile`, `dev`, `build`, `check`, and `lint` followed by `format` in `frontend/`. Only assistantbot has them; the recipes above are shared with the two libraries.

There is no lint target. Format with `clang-format -i <files>` (root `.clang-format`), and check with `clang-format --dry-run -Werror <files>`.

`.clang-format` sets `LineEnding: LF`, so the dry run flags every line of a CRLF file. `.gitattributes` (`* text=auto eol=lf`) overrides `core.autocrlf` and checks every file out with LF, Windows included. A working tree from before `.gitattributes` keeps its CRLF files until they are converted or checked out again.

Only these differ: the comments on the vcpkg commit and the CPM configure in `linux-ci.yml`, the CPM source cache steps around that configure, the `frontend` job and its `NODE_VERSION` in `linux-ci.yml`, the SQLite/Lua install and the `-drogon-sqlite3-lua-cpp` end of its cache key, the tag message, and the missing `include/**` path in `docs.yml`. Keep the three repos in step when changing them. `docs/*/ci.md` and `docs/*/doxygen.md` describe them for users; keep those pages in sync.

- `.github/workflows/linux-ci.yml` (Linux CI) runs on every branch push, PR, manual dispatch, and on version tags. It runs a `debug` and a `release` matrix leg on `ubuntu-24.04`.
  - Tools: CMake 4.2.3 (Kitware tarball, SHA-256 pinned) and LLVM 21 from apt.llvm.org (signing key fingerprint checked). `/usr/lib/llvm-21/bin` goes on `PATH`, so the presets' plain `clang++` resolves to LLVM 21.
  - Steps: `clang-format --dry-run -Werror` (debug leg only), then `vcpkg install 'drogon[sqlite3]' 'lua[cpp]'`, then `cmake --preset`, `cmake --build --preset`, and `ctest --preset`.
  - vcpkg is a shallow fetch of the pinned commit `67972e92`, the checkout that provides drogon 1.9.13 port-version 2. Bump `VCPKG_COMMIT` only after verifying locally on the same commit, and in all three repos.
  - Every run starts from an empty build tree. Configure sets `CPM_SOURCE_CACHE` to `$RUNNER_TEMP/cpm-source-cache`, which `actions/cache` restores before and saves after it, keyed on `CMakeLists.txt` and `cmake/CPM.cmake`. It holds CPM itself and the clones of the pinned library tags, so a cache hit clones nothing, and changing a pin changes the key.
  - The vcpkg binary cache is restored and saved with `actions/cache/restore` and `actions/cache/save` right after the install, so a failing build still keeps the dependencies.
  - On a tag, a step after configure compares the tag with `CMAKE_PROJECT_VERSION` from `CMakeCache.txt`.
  - The `frontend` job runs beside the matrix in `frontend/`: `pnpm/action-setup` installs the pnpm of `packageManager`, `actions/setup-node` installs Node.js `NODE_VERSION` (24) and caches the pnpm store keyed on `pnpm-lock.yaml`, then `pnpm install --frozen-lockfile`, `pnpm check`, and `pnpm build-only`.

## Build notes

- Requires CMake >= 4.0, Ninja, and ccache (hard-wired as `CMAKE_CXX_COMPILER_LAUNCHER`). Compiler is `clang++` on Linux, `clang-cl` on Windows.
- The UCRT deprecates `getenv`, and clang-cl warns about every call. The app uses `admin::read_env` (`_dupenv_s` on Windows, `getenv` elsewhere); reuse it rather than calling `std::getenv` directly.
- `CMAKE_CXX_STANDARD` is 26; standard-library features like `<print>` / `std::println` and `std::views::split` are in use.
- CI builds with clang 21 against Ubuntu 24.04's libstdc++ 14, older than the libstdc++ 15 or 16 a local machine may pick. A feature that compiles locally can fail there: clang rejects `| std::ranges::to<T>()` with libstdc++ 14 (`forward_like ... cannot be used before it is defined`), so `SessionStore::TakePending()` joins with a loop.
- Sources are picked up by `file(GLOB_RECURSE ... CONFIGURE_DEPENDS src/*.hpp src/*.cpp)`, so adding or removing source files triggers a re-configure on the next build. Ninja also re-configures when `CMakeLists.txt` changes.
- Everything except `src/main.cpp` goes into the OBJECT library `assistantbot-core`, which the executable and every test link. A STATIC library would let the linker drop controllers and plugins that register themselves through static objects.
- Precompiled headers are disabled in the base preset.

## Code style

New C++ code follows the `cpp-style-ref` skill (CMake + vcpkg variant). Its main rules:

- Naming: types PascalCase, public methods PascalCase, private methods camelCase, free helpers / variables snake_case, private members `m_`, constants UPPER_SNAKE, namespaces lowercase. Drogon's virtual overrides (`initAndStart`, `shutdown`) keep their upstream names.
- Every file starts with a `/** @file ... @brief ... */` block. Types and functions get multiline `/** ... */` Doxygen blocks, repeated on out-of-line definitions.
- `T const&` (const after the type), brace initialization (`int n{ 42 }`, `Json::Value body{}`), trailing return types.
- Wrap a function signature only when its one-line form exceeds 100 columns. Break after `(`, put one parameter per line, then `) const -> R {` on its own line. clang-format (`ColumnLimit: 0`) preserves this but won't create it.
- `.clang-format`: 4-space indent, no column limit, `InsertBraces: true`, `NamespaceIndentation: All`, left pointer alignment. It aligns trailing `///<` comments across blank lines, so give long constants a preceding doc block instead.
- `.clang-format` must only use keys supported by the local clang-format/clangd (21.x). A single unknown key (e.g. from a config dumped by clang-format 22+) makes clang-format reject the whole file, and clangd silently falls back to LLVM style (2-space indent). Check with `clang-format --dump-config src/main.cpp` after editing it.
- `CHECK` and `REQUIRE` are macros: a braced initializer with commas inside one splits the arguments, so build the expected value in a variable first.

### HTTP tracing

`admin/http_traces.*` retains 50 owned, redacted HTTP attempts. The source libraries are pinned to drogon-openai v0.3.0 and drogon-onebot v0.5.0. Use `admin::traced_model` and `traced_onebot` when constructing outgoing clients; reverse WebSocket actions emit no HTTP trace. Authentication configures secret redaction before listeners start. All three trace routes are protected by the existing pre-routing advice; downloads and DELETE are covered by `test_admin_http_traces`. Body prefixes are UTF-8 safe and omit credential fields and inline image data; traces may contain conversation text and are process-local. The frontend refreshes on small `http_trace_created` events rather than broadcasting bodies.

### Optional features and groups

`FeatureSettings` persists validated immutable sections with save-before-publish and revision conflicts. Credential fields accept environment names only. `feature_records` provides atomic document revisions; stale updates cannot recreate deleted documents. Groups default disabled, use typed membership, and pass enabled messages through `PrivateChat`; `Peer.group_id` selects group delivery. Positive friend keys and negative group keys keep histories distinct across session APIs, subscriptions, usage, and storage. Migration 6 adds actual sender/group fields to the append-only message log. Administrator QQs authorize group commands only; pause and sender blacklist precede commands. Tests cover malformed settings, snapshot ownership, document conflicts, API auth, group cards/prompts, command permissions, and context isolation.

### Favourites and character references

`AssetsController` calls only typed NapCat favourite extensions, exposing host-local file additions, resource deletion, and description changes. `character_image_bytes` validates bounded canonical base64 and static PNG/JPEG/WebP framing before saving the character document. Character replacement/deletion uses document revisions. Both configs allow 12 MiB request bodies for 8 MiB decoded references. The Assets page loads character data independently from favourite-extension failures. `test_admin_assets` covers authentication, malformed uploads, typed favourites, persistence, and stale writes/deletes.

### Model roles, memory, and scheduling

`ModelRoles` creates immutable per-request overrides for nine roles, clears inherited credentials at custom endpoints, resolves environment names, and records every network request including auxiliaries and failures. `AgentRuntime` owns one feature snapshot per reply and uses router/decision roles before a bounded executor/fallback loop. Incoming HTTP images can use the vision role before queuing. `PrivateChat::SendMessage` logs and appends typed tool deliveries as well as text. Text and quoted tool replies use the reply character limit, keeping a quote only on the first part; no tool may choose another conversation. Session history remains plain user/assistant turns and never loads from persistent chat records.

Schema 7 adds versioned `memories` with embedding space identity; schema 8 adds durable UTC `scheduled_tasks`. `MemoryService` injects labelled reference data, uses cosine recall only for compatible vector spaces, and extracts bounded per-sender batches with optimistic person updates. Affinity is independently optional. Reminder claims are atomic; startup marks interrupted running tasks failed instead of replaying uncertain deliveries. A timer keeps the scheduler alive only through a weak reference when idle. Actual handlers recheck pause and access. Drain `ScheduledTasks::Busy()` before stopping an app loop; storage continuations and the claimed-task callback must finish first.

### Tools and integrations

`tools/catalog.*` is the deterministic built-in catalog shared by validation, the editor, and runtime. Tools and optional roles start disabled. Schema/name validation precedes execution, only offered names may run, repeated call IDs cannot repeat effects, calls run sequentially, and tool exceptions become bounded results. Disabled memory or auxiliary roles remove their dependent tools. Source metadata supplies decimal message IDs and image counts; `ask_images` resolves zero-based indices against the source URLs without accepting arbitrary image URLs. MCP schemas are selected explicitly and retained for one reply only. The Streamable HTTP client supports explicit 2025-11-25 sessions and 2026-07-28 stateless metadata, bounded JSON/SSE responses, pagination, parameter headers, and best-effort session close. It never retries side effects.

Lua links vcpkg's `unofficial::lua::lua-cpp`, not the C ABI target: allocation/error unwinding must preserve C++ objects. Include the C++-compiled `lua.h` headers directly, not the extern-C wrapper. Every invocation owns a fresh state with allocation, instruction, active-time, host-operation, and JSON conversion budgets. Reserve Lua stack space during recursive conversion and push host results through protected calls. JSON null uses an opaque sentinel. Host operations yield to asynchronous HTTP, typed chat delivery, and scoped scheduling. Admin Lua tests mock all effects. `tools/http.*` must use `setContentTypeString`, because adding a Content-Type header alone leaves Drogon's default body type active. Lua HTTP trace source is `tool`.

New app-backed coverage includes `test_model_roles`, `test_admin_memory`, `test_admin_tasks`, `test_admin_tooling`, `test_mcp`, `test_agent`, and `test_agent_chat`; pure `test_lua` covers schema validation, isolation, yielding, and resource exhaustion. Do not run app-backed test executables concurrently outside CTest's listener resource lock. The Models, Memory, Tasks, Tools, and MCP pages use typed APIs and preserve string IDs/revisions. Keep both language guides synchronized with actual runtime limits.
